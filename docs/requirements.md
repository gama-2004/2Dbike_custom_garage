# 2Dカスタムガレージ 必要機能一覧

2026-10-22 作成

## 概要

卒業研究として完成させるには、全25機能のうち「必須」の10機能をそろえる必要があります。現プロトタイプで完了しているのはそのうち3機能です。

- **作るもの**: バイクを真横から見た2D図で、パーツと塗装を組み替えて仕上がりを確認できるWebアプリ
- **想定ユーザー**: カスタムを検討しているライダー、またはカスタムに興味のある初心者(仮)
- **研究上のねらい(仮)**: 実車を改造する前に、完成イメージと費用・注意点を把握できるようにすること
- **現在の位置づけ**: 見た目の組み替えを確かめるためのプロトタイプ。データ構造、評価の仕組み、書き出し機能はまだない

## 実装済み機能

現プロトタイプは1つのHTMLファイル(SVG描画、素のJavaScript)で動いています。

| 機能 | 内容 |
| --- | --- |
| ベース車両 | スーパースポーツ、アメリカンの2種。切り替えてもそれぞれの仕様を保持 |
| パーツ選択 | スーパースポーツ10部位、アメリカン13部位。各部位2〜4種類 |
| 塗装 | メイン・サブ・ラインの3色とグラフィック柄。フレーム、シート、リムなども個別に変更。任意色も指定可 |
| 車高 | ローダウン量をスライダーで変更 |
| プリセット | 車両ごとに5種類(サーキット仕様、ボバーなど)と、ランダム生成 |
| スタイル名の自動判定 | 組み合わせから「チョッパー」などを表示 |
| ビルドシート | 部品と色の一覧、シート高・最低地上高・車両重量の目安(仮の数値) |
| 車体クリック | 図のパーツを押すと、その設定欄へ移動 |
| 保存 | ブラウザ内に最大20件。呼び出しと削除 |
| 画面対応 | PCとスマホ、ライト／ダーク表示 |

## 必要機能の洗い出し

必須は10機能で、完了が3、一部実装が2、未着手が5です。優先度は、**必須** = 研究として成立させるのに欠かせない、**推奨** = あると評価が上がる、**発展** = 時間があれば取り組む、としています。

| ID | 分類 | 機能 | 内容 | 優先度 | 状況 |
| --- | --- | --- | --- | --- | --- |
| F-01 | 車両・パーツ | ベース車両の選択 | 車両ジャンルを切り替える | 必須○ | 実装済み |
| F-02 | 車両・パーツ | ベース車両の追加 | ネイキッド、オフロード、スクーターなど | 推奨△ | 未着手 |
| F-03 | 車両・パーツ | パーツ定義のデータ化 | パーツ・色・プリセットをJSONで管理し、コードを変えずに追加できるようにする | 必須○ | 未着手 |
| F-04 | 車両・パーツ | パーツ属性 | 各パーツに価格・重量・説明・適合車両を持たせる | 推奨△ | 一部(重量のみ) |
| F-05 | 車両・パーツ | 組み合わせ制約 | 同時に付けられないパーツを選べなくし、理由を表示する | 必須○ | 一部(スクリーンのみ) |

| F-10 | カスタム操作 | プリセット・おまかせ組み | 完成形から始める、ランダム生成 | 推奨△ | 実装済み |

| F-17 | 保存・共有 | 共有用コード | 仕様をURLや文字列にして他人に渡す | 推奨△ | 未着手 |

| F-20 | 情報提示 | 概算費用 | パーツ価格と工賃の合計(F-04が前提) | 推奨△ | 未着手 |

## 非機能要件

最も重要なのは、実在メーカーの車名・ロゴ・デザインをそのまま使わないことです。

| 項目 | 要件 | 現状 |
| --- | --- | --- |
| 著作権・商標 | 車両はジャンルを参考にしたオリジナルデザインにする。実車を扱う場合はメーカーの許諾を取る | 対応済み(オリジナル) |
| 対応端末 | PCとスマホの主要ブラウザ(Chrome、Safari、Edge)で動く | 対応済み |
| 応答速度 | パーツを変えてから図に反映されるまで0.1秒以内 | 測定していない |
| 操作性 | 初めての人が説明なしで5分以内に1台仕上げられる | 未検証 |
| アクセシビリティ | キーボードで全操作できる。色名を文字でも表示する | 一部対応 |
| 拡張性 | 車両やパーツの追加をデータの追加だけで済ませる(F-03) | 未対応(描画と定義が同じコード内) |
| 保守性 | ファイル分割、型付け(TypeScriptなど)、Gitでの履歴管理 | 未対応(1ファイル構成) |
| データ保存 | 保存先とその限界(ブラウザを消すと消えるなど)を利用者に示す | 一部対応 |
| 個人情報 | 操作ログを取る場合は、参加者の同意を得て匿名で記録する | 該当なし(ログ未実装) |

## 研究としての評価

卒業研究では「作った」だけでなく「役に立つかを確かめた」結果が必要なので、評価の方法を先に決めておくと、必要な機能(F-23〜F-25)も固まります。以下は評価方法の例です。

| 評価すること | 方法 | 必要な機能 |
| --- | --- | --- |
| 使いやすさ | 操作後にSUS(System Usability Scale、10問)で回答してもらう | F-25 |
| 作業効率 | お題を出し、完成までの時間と操作回数を測る | F-23、F-24 |
| イメージとの一致 | 「完成イメージをつかめたか」を5段階で聞き、写真カタログを見るだけの方法と比べる | F-09、F-25 |
| 情報の有用性 | 費用や注意表示を見て、判断が変わったかを聞く | F-20、F-22 |

参加者は、学内のバイク利用者を中心に10〜20名程度が現実的です。人数と評価項目は指導教員と相談して決めてください。

## 未決事項と次のステップ

決めること:

- 研究の問い: 「カスタム検討を支援できるか」を検証するのか、「2Dでの部品合成の仕組み」自体を成果にするのか
- 想定ユーザー: カスタム経験者か、初心者か
- 実車を扱うか: 扱うならメーカーへの許諾が必要
- 開発環境: 今の1ファイル構成を続けるか、ReactやTypeScriptで作り直すか
- 日程: 中間発表と卒論提出の日付

次にやること:

- [ ] 研究の問いと評価方法を指導教員と相談する
- [ ] 必須機能の優先順を確定する
- [ ] F-03(パーツ定義のデータ化)に着手する。他の機能の土台になるため
- [ ] F-08(元に戻す)とF-09(比較)を実装する
- [ ] 評価実験の前にF-23(操作ログ)を実装する
