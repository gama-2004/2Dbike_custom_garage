## 2-01 車両ベース選択

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | 車両ベース選択 |
| アクター | 利用者 |
| 概要 | カスタムの土台にするベース車両を一覧から選び、その標準仕様を車両ビュー・パーツ棚・ビルドシートに表示する。 |
| 事前条件 | データベースに公開中のベース車両が1台以上登録されている。 |
| 事後条件 | 選んだ車両の標準仕様(またはその車両で前回組んでいた仕様)が現在の仕様になり、画面がその車両の内容になる。変更履歴は空になる。 |

**基本フロー**

1. 利用者は車種選択画面、またはカスタム画面の「車種選択」タブを開く。
2. システムはサーバーから車両一覧を取得し(GET /api/vehicles)、車両の絵と名前を並べる。
3. 利用者は車両を選ぶ。
4. システムはその車両のカタログ(部位、パーツ、塗装部位、色、制約、プリセット、標準仕様)を取得する(GET /api/vehicles/{id}/catalog)。
5. システムは標準仕様の複製を現在の仕様にし、変更履歴を消す。
6. システムは車両図を描画して車両ビューに表示し、パーツ棚をその車両の部位で組み立て直す。

**代替フロー**

- 3a. その車両を前に組んでいた場合、システムは標準仕様ではなく、前回の仕様を現在の仕様にする(車両ごとに覚えておく)。
- 4a. 取得済みの車両の場合、システムはカタログを取得し直さない。
- 2a. サーバーにつながらない場合、システムは組み込みの2車種(スーパースポーツ、アメリカン)だけで続ける。

**例外フロー**

- 2b. 車両が1台も登録されていない場合、システムはE001を表示して終了する。

## 2-02 ベース車両追加

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | ベース車両追加 |
| アクター | 管理者 |
| 概要 | 管理者が車両定義ファイル(JSON)を読み込み、新しいベース車両をカタログに登録する。定義ファイルには諸元、部位とパーツ、塗装部位と色、標準仕様、プリセット、描画データを含む。 |
| 事前条件 | 管理者がログインしている(2-10)。 |
| 事後条件 | 新しい車両がデータベースに登録され、2-01の車両一覧に表示される。 |

**基本フロー**

1. 管理者はベース車両追加画面(SCR-06)で、車両定義ファイルを選ぶ。
2. システムはファイルを読み込み、内容を検証する(必須項目、コードの形式、部位・パーツ・色の重複、標準仕様がすべての部位を満たすか、描画データに危険な要素がないか)。
3. システムは検証結果を一覧で表示し、標準仕様で描画した車両図をプレビューする。
4. 管理者は「登録」を押す。
5. システムは定義をサーバーに送る(POST /api/admin/vehicles)。
6. サーバーは同じ検証をもう一度行い、1つのトランザクションで車両・部位・パーツ・塗装部位・色・制約・プリセット・標準仕様を登録する。
7. システムはI001を表示し、登録済みの車両の一覧を更新する。

**代替フロー**

- 4a. 同じ車両コードが登録済みの場合、システムはW003で上書きするかを確認する。管理者が「上書き」を選ぶと、overwrite=true を付けて5へ進む。取り消すと何も登録しない。
- 6a. 上書きの場合、保存仕様が参照している古いパーツは削除せず、公開フラグを0にして残す。

**例外フロー**

- 2a. 検証エラーがある場合、システムはE004と、エラーの項目と理由を表示し、「登録」を押せなくする。
- 6b. 組み込みの車両(V001、V002)を上書きしようとした場合、サーバーは登録を断り、理由を表示する。

## 2-03 パーツ追加

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | パーツ追加 |
| アクター | 管理者 |
| 概要 | 登録済みの車両に、新しいパーツ(名前、重量差、価格、描画データ)と、そのパーツに関わる組み合わせ制約を追加する。 |
| 事前条件 | 管理者がログインしている(2-10)。対象のベース車両が登録されている。 |
| 事後条件 | パーツと制約がデータベースに登録され、利用者のパーツ棚に選択肢として表示される。 |

**基本フロー**

1. 管理者はパーツ追加画面(SCR-07)で対象の車両を選び、パーツ定義ファイルを選ぶ。
2. システムはファイルを読み込み、内容を検証する(必須項目、部位の存在、描画データの形式、制約の相手のパーツがあるか)。
3. システムは標準仕様にこのパーツを付けた車両図をプレビューする。
4. 管理者は「登録」を押す。
5. システムは定義をサーバーに送る(POST /api/admin/vehicles/{id}/parts)。
6. サーバーは再検証してから、1つのトランザクションでパーツと制約を登録する。
7. システムはI001を表示する。

**代替フロー**

- 1a. 定義ファイルの部位がまだない場合、システムは新しい部位を作ってからパーツを登録する。新しい部位の標準パーツはこのパーツになる。
- 4a. 同じパーツコードが登録済みの場合、システムは上書きするかを確認する。取り消すと何も登録しない。

**例外フロー**

- 2a. 検証エラーがある場合、システムはE004と、エラーの項目と理由を表示し、登録しない。
- 2b. 制約の相手のパーツが存在しない場合、システムはエラーを表示し、登録しない。

図(プロトタイプのとき作ったもの): [ロバストネス図](svg/uc2_03_robustness.svg) ／ [シーケンス図](svg/uc2_03_sequence.svg)

## 2-04 組み合わせ制約

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | 組み合わせ制約 |
| アクター | 利用者(2-05、2-08から包含) |
| 概要 | パーツを変えるとき、その組み合わせが制約ルールに違反しないかを判定する。選べない選択肢は無効にし、理由を示す。 |
| 事前条件 | 2-05でパーツの変更が要求された、または2-08で保存仕様が呼び出された。 |
| 事後条件 | 違反がなければ変更が許可される。新しい仕様で選べなくなった選択肢はパーツ棚で無効になり、理由が表示される。 |

**基本フロー**

1. システムは現在の仕様に変更を加えた、仮の仕様を作る。
2. システムは車両の制約ルールをすべて評価する(EXCLUDE: 起点と相手を同時に付けられない。REQUIRE: 起点を付けるには相手が必要)。
3. 違反がなければ、システムは変更を許可する。
4. システムは仮の仕様で選べなくなる選択肢を求め、パーツ棚で無効にする。理由はその選択肢に表示する。

**代替フロー**

- 3a. 違反したルールが自動解決できる場合(例: ネイキッド化するとスクリーンを外す)、システムは相手のパーツを外した仕様で許可し、I005で知らせる。

**例外フロー**

- 3b. 自動解決できない違反がある場合、システムは変更を許可せず、E002でルールの説明文を表示する。

## 2-05 パーツ・塗装選択

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | パーツ・塗装選択 |
| アクター | 利用者 |
| 概要 | 部位ごとのパーツや塗装の色を選び、車両ビューとビルドシート(部品、価格、重量、シート高)にすぐ反映する。 |
| 事前条件 | 2-01でベース車両が選ばれている。 |
| 事後条件 | 現在の仕様が更新され、変更が履歴に1件積まれる。車両ビューとビルドシートが更新される。 |

**基本フロー**

1. 利用者はパーツ棚、または車両ビューの部位をクリックして、パーツを選ぶ。
2. システムは組み合わせ制約を判定する(2-04を包含)。
3. システムは変更前と変更後の仕様を、変更履歴として記録する。
4. システムは現在の仕様を変更後の仕様にし、ブラウザにも書いておく(再読み込みしても続きから使える)。
5. システムは車両図を描画し直し、ビルドシート(合計金額、車両重量、シート高、最低地上高)を計算し直して表示する。

**代替フロー**

- 1a. 塗装の色を選んだ場合、システムは制約判定をせずに3へ進む。
- 1b. プリセット・おまかせ組み・ノーマルに戻すを選んだ場合、システムは複数の部位をまとめて変え、変更履歴には1件として記録する。
- 1c. ローダウン量を変えた場合、システムはシート高と最低地上高からその量を引く。

**例外フロー**

- 2a. 制約に違反した場合、システムは2-04の結果(理由)を表示し、仕様を変えない。

図(プロトタイプのとき作ったもの): [ロバストネス図](svg/uc2_05_robustness.svg) ／ [シーケンス図](svg/uc2_05_sequence.svg)

## 2-06 取り消し

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | 取り消し |
| アクター | 利用者 |
| 概要 | 直前の変更を取り消す。取り消した変更はやり直すこともできる。 |
| 事前条件 | 変更履歴が1件以上ある(「元に戻す」ボタンが有効)。 |
| 事後条件 | 仕様が1つ前の状態に戻り、車両ビューとビルドシートが更新される。取り消した変更はやり直し用に残る。 |

**基本フロー**

1. 利用者は「元に戻す」を押す(またはCtrl+Z)。
2. システムは取り消し用の履歴から直前の変更を取り出す。
3. システムは変更前の仕様を現在の仕様にする。
4. システムは取り出した変更を、やり直し用の履歴に移す。
5. システムは車両図とビルドシートを更新し、ボタンの有効・無効を切り替える。

**代替フロー**

- 1a. 利用者が「やり直す」を押した場合(Ctrl+Shift+Z)、システムはやり直し用の履歴から変更を取り出し、変更後の仕様を現在の仕様にして、取り消し用の履歴に戻す。
- 補足. 新しい変更(2-05)を行うと、やり直し用の履歴は空になる。履歴は最大50件で、超えたら古いものから捨てる。

**例外フロー**

- 2a. 履歴が空の場合、ボタンは無効になっているため、この操作は行えない。

## 2-07 ビフォーアフター比較

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | ビフォーアフター比較 |
| アクター | 利用者 |
| 概要 | ベース車両の標準仕様(ビフォー)と現在の仕様(アフター)を並べて比べる。変更した部位、価格と重量の差も一覧で示す。 |
| 事前条件 | 2-01でベース車両が選ばれている。 |
| 事後条件 | 比較画面を閉じるとカスタム画面に戻る。比較によって仕様は変わらない。 |

**基本フロー**

1. 利用者は「比較」を押す。
2. システムは現在の仕様と、車両の標準仕様を取得する。
3. システムは両方の車両図を描画する。
4. システムは2つの仕様の差分(部位、変更前、変更後、価格差、重量差)を求める。
5. システムは2つの図を左右に並べ、差分の一覧と一緒に比較画面(SCR-02)に表示する。
6. 利用者は比較画面を閉じる。システムはカスタム画面に戻る。

**代替フロー**

- 2a. 利用者が保存一覧から比較相手を選んだ場合、システムは標準仕様の代わりにその保存仕様をビフォーとして使う(GET /api/builds/{id})。
- 5a. 利用者が「重ねる」を選んだ場合、システムは2つの図を重ね、スライダーで境目を動かして比べられるようにする。

**例外フロー**

- 4a. 差分がない場合、システムはI004を表示する。

## 2-08 仕様保存・呼出

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | 仕様保存・呼出 |
| アクター | 利用者 |
| 概要 | 現在の仕様に名前を付けてサーバーに保存し、あとで一覧から呼び出す。名前の変更と削除もできる。 |
| 事前条件 | 保存: 2-01でベース車両が選ばれている。呼出: 保存仕様が1件以上ある。 |
| 事後条件 | 保存: 保存一覧に1件追加される。呼出: 選んだ仕様が現在の仕様になり、車両ビューに表示される。削除: 一覧から消える。 |

**基本フロー**

1. 【保存】利用者は名前を入力して「保存」を押す(省略すると「ビルド #番号」)。
2. システムは現在の仕様とスタイル名を、利用者キー(X-Owner-Key)を付けてサーバーに送る(POST /api/builds)。
3. サーバーは1つのトランザクションで、仕様と保存仕様をデータベースに登録する。
4. システムはI002を表示し、保存一覧を更新する。

**代替フロー**

- 【呼出】A1. 利用者はマイページ(SCR-03)の一覧から仕様を選び、「読み込む」を押す。
- A2. システムは保存仕様を取得する(GET /api/builds/{id})。
- A3. 車両が現在と違う場合、システムは車両を切り替える(2-01の4〜6)。
- A4. システムは組み合わせ制約で整合性を確かめる(2-04を包含)。
- A5. システムは仕様を現在の仕様にし、変更履歴を消す。
- 【名前の変更】R1. 利用者は新しい名前を入力する。システムはサーバーの保存名を変える(PATCH /api/builds/{id})。
- 【削除】D1. 利用者は削除ボタンを押し、W002の確認に答える。システムはサーバーから削除し(DELETE /api/builds/{id})、I003を表示する。
- 2a. サーバーにつながらない場合、システムはブラウザ(localStorage)に保存する(最大20件)。

**例外フロー**

- 3a. 保存仕様が50件ある場合、サーバーは保存を断り、システムはE003を表示する。
- A4a. 公開を止めたパーツを含む場合、システムはその部位を標準パーツに置き換え、I006で知らせる。
- 2b. 通信に失敗した場合、システムはE008を表示する。

## 2-09 PDF保存

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | PDF保存 |
| アクター | 利用者 |
| 概要 | 完成した車両図とビルドシート(部品、色、諸元)を、1枚のPDFにして端末に保存する。 |
| 事前条件 | 2-01でベース車両が選ばれている。 |
| 事後条件 | PDFファイルが利用者の端末に保存される。仕様は変わらない。 |

**基本フロー**

1. 利用者は「PDF保存」を押す。
2. システムはPDF出力画面(SCR-04)を表示する(用紙の向き、ビフォー図を含めるか)。
3. 利用者は条件を選び、「出力」を押す。
4. システムは現在の仕様で車両図を描画し、画像に変換する。
5. システムは部品表、塗装、諸元(重量、シート高)の表を作る。
6. システムはタイトル、日時、図、表をA4の1ページに配置したPDFを作る(RPT-01)。
7. システムは「スタイル名_YYYYMMDD.pdf」という名前でPDFを渡す。

**代替フロー**

- 3a. 「ビフォー図を含める」を選んだ場合、システムは標準仕様の図も描画し、並べて配置する。

**例外フロー**

- 6a. PDFの作成に失敗した場合(日本語フォントが読み込めないなど)、システムはE005を表示する。
- 7a. ブラウザがダウンロードを許可しない場合、システムはPDFを新しいタブで開く。

## 2-10 管理者ログイン

| 項目 | 内容 |
| --- | --- |
| ユースケース名 | 管理者ログイン |
| アクター | 管理者 |
| 概要 | 管理者がログインIDとパスワードでログインし、管理画面(2-02、2-03)を使えるようにする。 |
| 事前条件 | 管理者のアカウントがデータベースに登録されている(初期化コマンド、または管理者追加コマンドで登録する)。 |
| 事後条件 | ログインに成功すると管理画面(SCR-06、SCR-07)を使える。ログアウトするか、30分操作がないとセッションが切れる。 |

**基本フロー**

1. 管理者は /admin を開く。システムはログイン画面(SCR-05)を表示する。
2. 管理者はログインIDとパスワードを入力し、「ログイン」を押す。
3. システムはサーバーに送る(POST /api/admin/login)。
4. サーバーはbcryptでパスワードを照合し、成功したら連続失敗回数を0に戻して最終ログイン日時を記録する。
5. サーバーはセッションを作り直して、Cookie(HttpOnly、SameSite=Strict)を返す。
6. システムは管理画面を表示する。

**代替フロー**

- 1a. すでにログインしている場合(GET /api/admin/me)、システムはログイン画面を出さずに管理画面を表示する。
- 6a. 管理者が「ログアウト」を押した場合、サーバーはセッションを消し、システムはログイン画面に戻る。

**例外フロー**

- 4a. ログインIDまたはパスワードが違う場合、サーバーは連続失敗回数を1増やし、システムはE006を表示する。
- 4b. 5回続けて失敗した場合、サーバーは15分間ロックする。ロック中はE007を表示する。
